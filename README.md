## 2. Исходные требования (практика 2)

### 2.1. Функциональные

| ID | Функция | Требование |
|---|---|---|
| FR-01 | Регистрация | Система должна создавать учётную запись пользователя по email и паролю. Email должен быть уникальным. |
| FR-02 | Авторизация | Система должна проверять учётные данные и выдавать механизм авторизации для последующих запросов. |
| FR-03 | Профиль | Авторизованный пользователь должен иметь возможность получить и изменить разрешённые данные собственного профиля. |
| FR-04 | Подписки | Пользователь должен иметь возможность создать, получить, изменить и удалить свою подписку. |
| FR-05 | Платежи | Система должна хранить платежи, связанные с подписками, и предоставлять историю платежей пользователя. |
| FR-06 | Расходы | Система должна рассчитывать сумму расходов пользователя за выбранный период и предоставлять агрегированную информацию по подпискам. |
| FR-07 | Разграничение доступа | Пользователь не должен получать доступ к подпискам, платежам и аналитике другого пользователя. |
| FR-08 | Валидация | Система должна проверять обязательные поля и корректность значений входных данных до выполнения операции. |

### 2.2. Нефункциональные

| ID | Категория | Требование |
|---|---|---|
| NFR-01 | Безопасность | Пароли хранятся только в виде криптографического хеша; приватные данные пользователя недоступны другим пользователям. |
| NFR-02 | Надёжность | Подтверждённые операции записи не должны теряться при кратковременных сбоях отдельных компонентов. |
| NFR-03 | Согласованность данных | Повторная обработка одного и того же платежа не должна создавать дубликат платежа. |
| NFR-04 | Производительность | API обеспечивает приемлемое время ответа для штатной нагрузки, согласованной для проекта. |
| NFR-05 | Тестируемость | Основная бизнес-логика доступна для автоматического модульного и интеграционного тестирования. |
| NFR-06 | Сопровождаемость | Контракты endpoint-ов, модели запросов/ответов и правила ошибок явно документированы. |

### 2.3. Общие требования

- Операции над подписками и платежами выполняются в контексте авторизованного пользователя.
- Каждая подписка связана ровно с одним пользователем, каждый платёж — с одной подпиской.
- Суммы не отрицательны; валюта и периодичность передаются в согласованном формате.
- Удаление или деактивация подписки не удаляет исторические платежи.
- При некорректном запросе возвращается понятный код HTTP и описание ошибки без внутренних деталей сервера.

### 2.4. Endpoint-ы и модель данных

Endpoint-ы: `POST /api/auth/register`, `POST /api/auth/login`, `GET` и `PATCH /api/users/me`, `GET` и `POST /api/subscriptions`, `GET`, `PATCH` и `DELETE /api/subscriptions/{id}`, `GET /api/payments`, `GET /api/analytics/expenses`.

Сущности: User (id, email, passwordHash), Subscription (id, userId, name, amount, currency, period, startDate, status), Payment (id, subscriptionId, amount, currency, paymentDate, status, externalId). Связи: User 1—* Subscription 1—* Payment.

Коды ответа: 200/201, 400, 401, 403, 404, 409, 422, 500.

## 4. Итоговые требования (реализованы в коде)

### 4.1. Правила данных

- `email`: приводится к нижнему регистру, уникален; пароль 8–128 символов, хранится как PBKDF2-хеш.
- `name`: 1–100 символов; `amount`: от 0 до 1 000 000 000; `currency`: три латинские буквы (приводятся к верхнему регистру); `period` ∈ Weekly, Monthly, Quarterly, Yearly; `startDate` и `paymentDate` обязательны.
- Статус подписки при изменении: Active, Paused, Cancelled; `Deleted` — только через `DELETE`.
- Статус платежа: Pending, Succeeded (по умолчанию), Failed.
- `externalId` платежа: 1–100 символов, глобально уникален.

### 4.2. Поведение

- Чужой ресурс — 403; несуществующий или удалённый — 404; ошибки валидации — 422; неразбираемый запрос — 400; занятый email и `externalId` другой подписки — 409.
- Платёж с уже существующим `externalId` той же подписки возвращает существующую запись (200), дубликат не создаётся.
- Аналитика расходов: только платежи Succeeded, границы периода включительно, суммы по валютам не смешиваются; `dateFrom` и `dateTo` обязательны.
- Платежи удалённой подписки сохраняются и доступны в истории; записать новый платёж в удалённую подписку нельзя (404).

### 4.3. Endpoint-ы

Полная спецификация — в [`API.md`](API.md). Относительно практики 2 добавлен один endpoint: `POST /api/subscriptions/{id}/payments`.
