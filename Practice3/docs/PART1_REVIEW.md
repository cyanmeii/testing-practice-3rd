# Часть 1 — ответы и ревью

## 1. Тесты для `PrimesAmount.CountPrimesAmount` (`part1/Part1.Tests/PrimesAmountTests.cs`)
Что учтено из-за асинхронности/параллелизма (`Parallel.For`):
- порядок элементов в `ConcurrentQueue` не определён -> сравнение как множеств (`CollectionAssert.AreEquivalent`);
- зависимость вызывается из разных потоков -> счётчики вызовов в `ConcurrentBag`/`Interlocked`;
- при исключении в итерации `Parallel.For` кидает `AggregateException`; метод его глушит и очищает очередь (даже найденные простые) -> результат пуст, причина потеряна (в коде `//TODO`);
- `ClearCache` в `finally` должен вызываться один раз и строго после всех проверок (тест фиксирует число завершённых проверок на момент вызова).

**Неопределённость/дефекты исходного кода (то, о чём говорил преподаватель):**
1. Конструктор проверяет поле `border` (всегда 0), а не параметр `pborder` -> бросает исключение при любом значении. Исправлено в одну строку (см. README, п. 7).
2. Верхняя граница исключена: `Parallel.For(2, border)` не проверяет само `border`; в документации поведение не определено.
3. `ConcretePrimeService.CheckIsPrime(2)` возвращает `false` (условие `p%2!=0`) -> двойка никогда не попадает в результат.
4. Свойство `Count` недостижимо: поле `count` нигде не присваивается, `Count` всегда бросает `Exception("count is not set")`.
5. `null`-сервис не проверяется: при `border > 1` наружу вылетает `NullReferenceException` из `finally`.
6. При `border <= 1` `ClearCache` не вызывается, при `border >= 2` — вызывается (неоднородно).

Тесты `*_KnownDefect` проходят на текущем коде и документируют дефект; после исправления их нужно инвертировать.

## 2. Тесты блока 5 «Reserve inventory» (`ReserveInventoryBlockTests.cs`)
Покрыто (12 тестов): порядок и количество резервов; токен вызывающего передаётся в `TryReserveAsync`; отсутствие `Release`/успешный переход к оплате; отказ на первой/средней/последней позиции (освобождаются только уже зарезервированные, в порядке резервирования, дальнейшие не резервируются, платёж и сохранение не вызываются); сообщение и `FailureReason.OutOfStock`; откат с `CancellationToken.None`; один SKU в двух строках; сбой `Release` при откате (остальные освобождаются, ошибка логируется, результат прежний); граница с блоком 4 (дорогой заказ не резервирует склад).
**Найденный дефект:** если `TryReserveAsync` бросает исключение (в т.ч. `OperationCanceledException`), уже зарезервированные позиции не освобождаются — утечка резерва (`..._KnownDefect`). Рекомендация: обернуть цикл в `try/catch` и откатывать `reserved`.

## 3. Ревью `OrderProcessingServiceTests.cs`
Оценка сделана по структуре набора: имена всех тестов, `SetUp` и ключевые блоки; каждую строку я не разбирала.

**Это юнит-тесты?** Да: тестируется один класс, все 10 зависимостей заменены на Moq (в т.ч. `IClock` и `IDelayer`, поэтому нет реального времени и ожидания), нет I/O, результат детерминирован. Это не интеграционные тесты.

**Сильные стороны:** граничные значения (50/51 строк, ровно порог ручной проверки, ровно 3 попытки), параметризация, проверка линейного backoff без реальных задержек, компенсации при сбое сохранения, токены отмены, best-effort уведомление.

**Проблемы, требующие доработки:**
1. Файл не компилируется: на строках 527–528 подряд два атрибута `[Test]` (ошибка CS0579, дубликат атрибута).
2. Один «монолитный» класс на ~800 строк и общий `SetUp` из 10 моков — трудно читать; лучше разнести по блокам (валидация, скидки, резерв, оплата, сохранение, уведомление).
3. Переспецификация: много `Verify(..., Times.Never())` и тест порядка шагов делают набор хрупким к безобидному рефакторингу.
4. Проверка логов через `Mock<ILogger>` (`VerifyLogged`) завязана на реализацию логирования.
5. Часть тестов фиксирует сомнительное поведение как «ожидаемое» (напр. сбой `Refund` пропускает освобождение склада; утечка резерва при исключении в блоке 5 не покрыта вовсе).
6. Фреймворк NUnit, тогда как в курсе используется MSTest — несоответствие стеку практик.

**Полнота покрытия:** высокая для бизнес-веток `PlaceOrderAsync`. Не видно тестов на: `request.Customer == null` (NRE), исключение из `IDiscountEngine`/`ITaxCalculator`, отрицательный итог при скидке, сбой `ExecuteAsync` в ветке ручной проверки (блок 4), `TryReserveAsync` с исключением (см. п. 2), гонку при идемпотентности (два параллельных запроса с одним ключом), `OperationCanceledException` во время оплаты. Для точной цифры нужно запустить coverlet — по ветвям/строкам `OrderProcessingService`.

## 4. Ревью `BinaryMaxHeapTests`
Набор уже обширный (≈90 атрибутов тестов: конструкторы, индексатор, `Initialize`, `Add`, `Peek`, `RemoveMax`, `ExtractMax`, `Clear`, `Union`, `ToMinHeap`, Moq-проверки компаратора). Выводы (по замечаниям преподавателя):

1. **Проверять инвариант, а не только публичные результаты `Peek`/`ExtractMax`.** Хелпер `IsMaxHeap` (родитель ≥ потомков) есть, но используется всего в ~9 местах; его нужно вызывать после *каждой* мутирующей операции (`Initialize`, `Add`, `RemoveMax`, `ExtractMax`, `Union`, сеттер индексатора, `RebuildHeap`) и в параметризованных/случайных тестах. Результат `ExtractMax` сам по себе не доказывает, что структура в порядке.
2. **Покрыть структуру:** выбор левого и правого ребёнка (когда больше правый), восстановление на нескольких уровнях (≥ 3 уровня: 15 элементов), повторное извлечение максимума до пустой кучи, добавление в кучу разного размера, пустая и одноэлементная куча, дубликаты, отрицательные значения/`int.MinValue`, `Add` после серии `ExtractMax`.
3. **Дефект `Initialize` с пустой коллекцией.** Реализация делает `if (newCollection.Count > 0) {...}`, поэтому `Initialize(пустой список)` *не очищает* прежнее содержимое, тогда как непустая коллекция его заменяет. Текущий тест `Initialize_EmptyCollection_LeavesExistingContentsUntouched` фиксирует это как норму; он должен ожидать `IsEmpty == true` и падать, пока реализация не исправлена. Исправление в коде указывать отдельным пунктом отчёта.

Дополнительно: нет теста на `Initialize(null)` (сейчас `NullReferenceException` без проверки аргумента); нет теста на устойчивость `Union` к одной и той же куче, переданной дважды; стоит добавить тест на стабильность при компараторе, бросающем исключение.
